# manifold — 拆开世界，再重建

## 1. 项目定位

**AdventureX 2026：manifold / 软件方向**

**一句话介绍：**  
用户上传图片或输入文字，系统判断对象属于“物体”还是“生命”，再按照不同逻辑将其拆成当前理解所需的有意义单元，不设固定数量上限，重点展示单元之间的联系；用户可以逐层深入，并在物体模式中查看如何将其重新组建。

**核心愿景：**

> 拆开世界，看见联系，再重新组建。

当前版本只制作**网站框架和交互原型**：

- 使用静态数据；
- 不接入 AI API；
- 不生成任何图片；
- 不追求识别任意对象；
- 先验证“拆解—理解关系—重建”的产品体验。

---

## 2. 要解决的问题

### 2.1 AI 给出了答案，但知识仍然是断开的

普通 AI 通常使用连续文字回答。它可以告诉用户一个对象包含哪些部分，却很难让用户直观看清：

- 每个部分处于什么位置；
- 部件之间如何连接；
- 信息、能量或物质如何流动；
- 哪个部件控制、影响或依赖哪个部件；
- 当前理解到了哪一层；
- 下一步应该继续探索什么。

manifold 将文字回答转化为可探索的关系图。

### 2.2 AI 能给出零件和教程，但新手仍然不容易做出来

新手面对一堆零件时，真正缺少的通常不是更多文字，而是：

- 每个零件承担什么作用；
- 零件之间应该怎样连接；
- 为什么必须这样连接；
- 应该先完成哪一个最小模块；
- 每一步怎样确认自己做对了；
- 失败后应该检查哪里。

manifold 希望把“教程”转化为一条可以逐步验证的重建路径。

## 3. 核心规则

### 3.1 每层按理解所需展示单元

manifold 的信息组织规则不依赖固定节点数量：

- 每一层展示完成当前理解所需的关键单元，不设固定数量上限；
- 不为了凑固定数量而创造不存在的结构；
- 点击任意单元后，可以继续进入下一层；
- 用户始终能够看见自己所处的层级与探索路径。

### 3.2 最小单元由用户目标决定

系统不默认一直拆到原子层面，而是根据目标决定停止位置。

- **了解模式：**停在足以解释工作原理的单元；
- **制作模式：**停在能够购买、加工或连接的零件；
- **维修模式：**停在能够检查或替换的部件；
- **生命模式：**根据对象停在器官、组织、细胞或其他有意义层级。

用户也可以手动指定希望拆解到什么程度。

### 3.3 关系比零件列表更重要

关系图中的连线必须具有明确含义。

**物体模式的关系类型：**

- 组成
- 支撑
- 供电
- 控制
- 感知
- 传递信号
- 传递能量
- 产生运动
- 保护
- 依赖
- 可替代

**生命模式的关系类型：**

- 组成
- 调节
- 运输
- 交换
- 信号传递
- 保护
- 支撑
- 产生
- 消耗
- 依赖

### 3.4 当前版本由代码和静态数据驱动

当前原型不让 AI 自由决定页面结构。

流程为：

1. 用户进入输入页；
2. 选择预置案例，或模拟上传图片、输入文字；
3. 页面读取本地 JSON 数据；
4. 图形引擎根据节点和关系绘制关系图；
5. 用户点击节点继续展开；
6. 用户切换不同关系视图；
7. 用户进入重建页面查看零件和步骤。

静态数据与页面组件必须分离，后续才可以把静态数据源替换为 AI 或后端 API。

## 4. 目标用户

### 核心用户

- 对现实物体工作原理感到好奇的人；
- 刚开始接触硬件、Maker 和 DIY 的新手；
- 需要通过图形理解复杂结构的学生。

### 次级用户

- 初级维修学习者；
- 需要展示系统结构的教师和内容创作者。

## 5. 产品模式

### 5.1 物体模式

适用于自动垃圾桶、风扇、自行车、键盘、机器人等。

主要展示：

- 组成结构；
- 信号流；
- 能量流；
- 机械运动；
- 控制链路；
- 制作路径；
- 维修检查路径。

### 5.2 生命模式

适用于叶片、眼睛、心脏、昆虫等。

主要展示：

- 层级结构；
- 物质交换；
- 信号与调节；
- 各部分的功能与依赖关系。

生命模式中的“重建”仅表示：

- 教学模型；
- 结构模拟；
- 安全观察任务；
- 非生命的仿生装置。

不提供制造真实生命体或危险生物实验方案。

## 6. 核心用户流程

### 6.1 拆开

1. 用户进入输入页面；
2. 选择图片上传、文字描述或预置案例；
3. 系统展示“物体 / 生命”的分类结果；
4. 用户可以手动纠正；
5. 用户选择目标：了解、制作或维修；
6. 系统按当前理解目标展示第一层核心单元；
7. 用户点击节点继续向下探索；
8. 用户可以切换关系视图：
   - 结构
   - 信号
   - 能量 / 物质
   - 因果
9. 用户随时通过面包屑或缩略路径返回上层。

### 6.2 理解一个节点

点击节点后，侧边栏展示：

- 节点名称；
- 简短功能；
- 所处层级；
- 与其他节点的关系；
- 上游与下游；
- 是否能够继续展开；
- 是否可以购买、替换或制作；
- 静态资料来源；
- 已观察 / 已验证 / 推断状态。

### 6.3 重建

物体模式中，用户可以点击“重建它”。

页面展示：

1. 简化后的制作目标；
2. 零件清单；
3. 每个零件的功能；
4. 零件之间的连接关系；
5. 工具和成本；
6. 分阶段制作步骤；
7. 每一步的完成标准；
8. 常见错误与排查路径；
9. 安全提示。

当前原型只为经过人工整理的预置案例提供重建内容。

### 7.1 当前版本必须完成

- 图片上传和文字输入的界面框架；
- 预置案例选择；
- 物体 / 生命分类结果页面；
- 用户手动纠正分类；

## 9. 技术框架

### 9.1 推荐技术

- React
- TypeScript
- Vite
- React Flow：节点和关系图
- Zustand：当前案例、视图和探索路径状态
- Tailwind CSS：基础样式
- Framer Motion：节点展开与页面过渡
- Vitest：领域规则测试

当前版本不需要后端。

### 9.2 架构原则

#### 数据层

负责读取不同案例的静态 JSON。

```ts
interface GraphRepository {
  getCase(caseId: string): Promise<WorldCase>;
  getNode(caseId: string, nodeId: string): Promise<GraphNode>;
  getBuildGuide(caseId: string): Promise<BuildGuide | null>;
}
```

先实现：

```ts
class StaticGraphRepository implements GraphRepository {}
```

未来需要接入 AI 或服务器时，只增加新的 Repository，不修改主要页面组件。

#### 领域层

负责真正体现项目思想的规则：

- 每层节点按理解所需展示，不设固定数量上限；
- 不允许不存在的关系类型；
- 每条边必须包含解释；
- 节点需要记录父级和层级；
- 不同模式使用不同关系集合；
- 重建步骤必须具有前置条件和验收标准。

#### 展示层

负责：

- 图谱布局；
- 节点展开动画；
- 关系视图切换；
- 侧边栏；
- 路径导航；
- 重建步骤展示。

展示层不得修改原始数据，只根据领域状态渲染。

### 9.3 核心数据结构

```ts
type DomainType = "object" | "life";
type NodeStatus = "observed" | "verified" | "inferred";

type RelationType =
  | "contains"
  | "supports"
  | "powers"
  | "controls"
  | "senses"
  | "signals"
  | "transfers_energy"
  | "transports"
  | "regulates"
  | "protects"
  | "depends_on"
  | "transforms";

type GraphNode = {
  id: string;
  parentId: string | null;
  label: string;
  summary: string;
  domain: DomainType;
  level: number;
  function: string;
  status: NodeStatus;
  canExpand: boolean;
  buildability: "safe" | "guided" | "not_recommended";
};

type GraphEdge = {
  id: string;
  source: string;
  target: string;
  relation: RelationType;
  explanation: string;
  views: Array<"structure" | "signal" | "energy" | "matter" | "causal">;
};

type BuildStep = {
  id: string;
  title: string;
  purpose: string;
  prerequisites: string[];
  instructions: string[];
  successCriteria: string[];
  troubleshooting: string[];
};

type WorldCase = {
  id: string;
  title: string;
  domain: DomainType;
  rootNodeId: string;
  nodes: GraphNode[];
  edges: GraphEdge[];
};
```

## 10. 对官方“代码诗意”的回应

当前项目不依赖大量 AI 调用，而把核心能力写进代码本身：

1. **按需组织单元：**将复杂对象整理为当前理解所需的局部结构；
2. **类型化关系：**每条边都表达真实意义；
3. **分层展开：**只加载和展示当前需要理解的部分；
4. **多视图过滤：**同一图谱可以观察结构、信号和能量关系；
5. **领域模型分离：**物体和生命使用不同的关系规则；
6. **Repository 抽象：**静态数据与未来 AI 数据可以替换；
7. **重建状态结构：**教程由步骤、前置条件、验收和排错组成。

项目的技术亮点不是“调用了多少模型”，而是把一种理解世界的方法编码成稳定、清晰、可扩展的软件结构。

## 12. 成功指标

- 用户在 10 秒内理解产品是做什么的；
- 每一层按理解所需展示节点，不设固定数量上限；
- 用户能够在 3 次点击内找到某个部件的作用和上下游；
- 用户能明显看出结构关系和信号关系的区别；
- 物体模式与生命模式呈现不同的拆解逻辑；
- 静态案例完全由 JSON 驱动；
- 新增一个案例时，不需要修改核心页面组件；
- 垃圾桶案例能够完整走通“拆开—理解关系—重建”流程。

## 13. Codex 实现要求

1. 只实现静态网站框架，不接入 AI 和后端；
2. 使用 React、TypeScript、Vite 和 React Flow；
3. 所有案例保存在独立 JSON 或 TypeScript 数据文件中；
4. 禁止在页面组件中写死节点和关系；
5. 先完成自动垃圾桶，再完成叶片案例；
6. 实现物体和生命两套关系过滤规则；
7. 领域层不设置固定子节点数量上限，节点数量服务于理解目标；
8. 每条关系必须具有类型和解释；
9. 实现结构、信号、能量 / 物质视图切换；
10. 实现节点展开、详情侧栏、面包屑和重建页面；
11. 页面刷新后仍能通过 URL 恢复当前案例和节点；
12. 为层级结构、关系类型和案例读取编写测试；
13. README 说明项目结构、运行方式、数据格式和新增案例的方法。
